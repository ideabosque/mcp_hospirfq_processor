## 2. Purpose and Scope

This SOP defines the ordered live integration scenarios used to validate `mcp_hospirfq_processor` against the local `silvaengine_gateway` route for `rfq_engine`, using **real B2B multi-vendor distributor catalog data** derived from the Shopify product export `products_export_1.csv`. All item names, vendor names, product types, and descriptions are in **English** — reflecting the actual DDS (Distributor Data Solutions) marketplace dataset spanning industrial tools, electrical devices, plumbing supplies, HVAC equipment, water treatment systems, PPE, and accessories.

Data is sourced from two directories:

- **Product data** (items, provider items, batches, price tiers, cancellation policies, catalog refs) comes from `sample_dataset/dds_dataset/` — generated from the real Shopify CSV export. The dataset also includes KGE/Neo4j graph ingestion for products, customers, and promotions.
- **Non-product operational data** (segments, segment contacts, seeded requests, seeded quotes, seeded quote items, FX rates, discount prompts) comes from the parent `prepare_test_data/` directory — generated by the existing Faker-based prepare scripts.

The product dataset covers 1,190 items (catalog SKUs), 1,190 provider items (vendor offerings), 1,190 provider item batches (stock lots with 25–500 units each), 10,710 item price tiers (3 segments × 3 volume breaks × 1,190 items), 3 cancellation policies (Standard 30-Day Return, Restocking Fee 15%, Non-Returnable), 1,190 catalog refs (namespace `DDS`, KGE-ingested and matched), and 0 bundles. The non-product dataset covers 3 segments with 15 contacts, 5 seeded requests, 11 seeded quotes, 6 seeded quote items, 16 FX rates, and 59 discount prompts (3 global + 6 segment + 25 item + 25 provider-item). All product prices are in **USD**; non-product operational data also uses **USD** as base currency.

- **In scope:** MCP HospiRFQ processor facade, GraphQL client path through the gateway, catalog-first item discovery from the `DDS` namespace, item/provider lookup, RFQ request lifecycle, quote lifecycle with unit pricing, pricing (price tiers + discount prompts), installments, files, segments, availability holds, cancellation policies (Standard 30-Day Return, Restocking Fee 15%, Non-Returnable), and catalog inquiry. KGE graph sync coverage for products, customers, and promotions.
- **Out of scope:** production testing, destructive cleanup of generated live test records, cloud provisioning, third-party production side effects, UI testing, load testing, MCP HTTP transport testing (covered by `integration_scenarios_sop_http.md`), direct database connection from the test runner (reconciliation is API-level only), data migration between backends, backend tuning/HA configuration, bundle and bundle component testing (DDS dataset has 0 bundles).
- **System(s) under test:** `mcp_hospirfq_processor`, local `silvaengine_gateway`, `rfq_engine`, `knowledge_graph_engine` (KGE/Neo4j), and catalog/KGE-backed inquiry path reachable through `rfq_engine`.

## 2.1 Controlling End-to-End Testing Procedure

The following procedure is authoritative for this DDS-dataset SOP:

1. Confirm the gateway is running and reachable before any test execution (environment validation gate).
2. When the backend is PostgreSQL, confirm the schema is at the latest Alembic revision (`alembic -c migration/alembic.ini upgrade head` applied) before any tool execution (migration readiness gate — dependency state `initialized`).
3. Confirm the prepared **non-product** data fixtures (`segments_and_contacts.json`, `requests.json`, `quotes.json`, `quote_items.json`, `fx_rates.json`, `discount_prompts.json`) from `prepare_test_data/` have been loaded via their respective prepare scripts.
4. Confirm the prepared **product** data fixtures (`dds_products.json`, `dds_catalog_refs.json`) from `sample_dataset/dds_dataset/` have been loaded via the DDS prepare scripts.
5. Confirm the KGE graph sync has been run (`prepare_dds_graph_sync.py`) so that customer, promotion, and (optionally) price-tier entities are ingested into Neo4j.
6. Execute the end-to-end live integration testing with the script `mcp_hospirfq_processor/tests/run_integration.py`, which drives the processor tools in-process through the gateway GraphQL route.
7. Use variables from `mcp_hospirfq_processor/tests/.env` to target the local integration instance. Do not hard-code credentials, endpoint IDs, partition IDs, gateway URLs, or `DATABASE_URL` values in generated reports.
8. Read and use the prepared data in `sample_dataset/dds_dataset/` (product) and `prepare_test_data/` (non-product) as the reference dataset and dependency source for function inputs, expected relationships, and scenario ordering.
9. Before any item/request/quote workflow is executed, perform catalog search first (`inquire_catalog` with namespace `DDS`) and use the catalog result to identify the primary item and provider item for the remainder of the test run.
10. Reconcile the catalog result to prepared data in `dds_catalog_refs.json`, so the selected catalog node maps back to known `itemUuid`, `providerItemUuid`, vendor, and product reference data.
11. Build the function dependency map before execution, then derive the test sequence priority from that dependency map rather than file-discovery order.
12. Perform end-to-end live integration testing in dependency order.
13. Address any implementation, runner, data-contract, repository, or scenario-ordering issues found during live execution.
14. Retest affected scenarios, then rerun the full dependency-ordered suite until all required calls pass with zero unexpected error responses.
15. Export the final per-function arguments and outputs into the project `docs/` directory as a dated results file.

## 6. Execution Order

```text
catalog_discovery -> items -> requests -> quotes -> pricing -> installments -> files -> segments -> availability -> cancellation -> catalog
```

**Reason for deviation from default:** this project is an RFQ processor facade; catalog discovery must identify the primary item before item/provider validation and request creation, request/provider assignment must precede quote creation, quote pricing must precede installment validation, and cancellation/catalog readbacks are reference checks. Bundle scenarios are omitted (DDS dataset has 0 bundles). The sequence does not change with backend selection — it only changes where data is persisted.

**Sequence construction rule:** the execution order must be rebuilt or revalidated before each certification run from the actual function dependencies in the runner and codebase. Static file order is not sufficient.
