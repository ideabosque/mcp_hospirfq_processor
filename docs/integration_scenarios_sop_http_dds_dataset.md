## 2. Purpose and Scope

This SOP defines the ordered live integration scenarios used to validate `mcp_hospirfq_processor` through the **MCP HTTP transport layer** — the same JSON-RPC path (`initialize`, `tools/list`, `tools/call`) that a real AI agent uses to invoke tools via the gateway REST endpoint — using **real B2B multi-vendor distributor catalog data** derived from the Shopify product export `products_export_1.csv`. All item names, vendor names, product types, and descriptions are in **English** — reflecting the actual DDS (Distributor Data Solutions) marketplace dataset spanning industrial tools, electrical devices, plumbing supplies, HVAC equipment, water treatment systems, PPE, and accessories.

Data is sourced from two directories:

- **Product data** (items, provider items, batches, price tiers, cancellation policies, catalog refs) comes from `sample_dataset/dds_dataset/` — generated from the real Shopify CSV export. The dataset also includes KGE/Neo4j graph ingestion for products, customers, and promotions.
- **Non-product operational data** (segments, segment contacts, seeded requests, seeded quotes, seeded quote items, FX rates, discount prompts) comes from the parent `prepare_test_data/` directory — generated by the existing Faker-based prepare scripts.

The product dataset covers 1,190 items (catalog SKUs), 1,190 provider items (vendor offerings), 1,190 provider item batches (stock lots with 25–500 units each), 10,710 item price tiers (3 segments × 3 volume breaks × 1,190 items), 3 cancellation policies (Standard 30-Day Return, Restocking Fee 15%, Non-Returnable), 1,190 catalog refs (namespace `DDS`, KGE-ingested and matched), and 0 bundles. The non-product dataset covers 3 segments with 15 contacts, 5 seeded requests, 11 seeded quotes, 6 seeded quote items, 16 FX rates, and 59 discount prompts (3 global + 6 segment + 25 item + 25 provider-item). All product prices are in **USD**; non-product operational data also uses **USD** as base currency.

Unlike the companion in-process SOP (which calls `MCPHospiRFQProcessor` methods directly in-process and configures GraphQL access), this SOP exercises only the `MCPHttpClient → gateway /mcp → dispatch_mcp → MCPHospiRFQProcessor` path. No GraphQL endpoints, `GraphQLClient` configuration, or `rfq_engine` imports are involved from the test script's perspective — the gateway handles backend dispatch internally.

- **In scope:** MCP JSON-RPC protocol (initialize, tools/list, tools/call), gateway MCP dispatch layer, `MCPHttpClient` async transport, SSE/JSON response parsing, Bearer token auth through `MCPHttpClient`, all 38 processor tools across 11 tool groups, English product data validation, DDS marketplace catalog namespace validation, KGE graph sync coverage.
- **Out of scope:** production testing, destructive cleanup of generated live test records, cloud provisioning, third-party production side effects, UI testing, load testing, direct in-process method calls (covered by companion in-process SOP), GraphQL endpoint configuration (handled internally by the gateway), data migration between backends, backend tuning/HA configuration, bundle and bundle component testing (DDS dataset has 0 bundles).
- **System(s) under test:** `mcp_http_client.MCPHttpClient`, `silvaengine_gateway` REST MCP route (`/{endpoint_id}/mcp` with `Part-Id` request header), `mcp_daemon_engine` dispatch, `mcp_hospirfq_processor`, `knowledge_graph_engine` (KGE/Neo4j, reachable through gateway backend dispatch).
- **Transport validation:** this SOP validates that the gateway correctly dispatches JSON-RPC `tools/call` requests to the MCP daemon engine, which instantiates and invokes `MCPHospiRFQProcessor` methods, serializes results into MCP `content` arrays, and returns them over HTTP. The test script never accesses GraphQL directly.

## 2.1 Controlling End-to-End Testing Procedure

The following procedure is authoritative for this DDS-dataset MCP HTTP transport SOP:

1. Execute the end-to-end live integration testing with the script `mcp_hospirfq_processor/tests/run_http_integration.py`, which uses `MCPHttpClient` to drive all tool calls through the gateway REST/JSON-RPC MCP endpoint.
2. Use variables from `mcp_hospirfq_processor/tests/.env` to target the local integration instance. Do not hard-code credentials, endpoint IDs, partition IDs, gateway URLs, or `DATABASE_URL` values in generated reports.
3. Read and use the prepared data in `sample_dataset/dds_dataset/` (product) and `prepare_test_data/` (non-product) as the reference dataset and dependency source for function inputs, expected relationships, and scenario ordering.
4. Before any tool group is executed, verify that `MCPHttpClient` can successfully complete the JSON-RPC `initialize` handshake with the gateway. This confirms the MCP transport layer is operational.
5. Optionally run with `--list-tools` to verify that `tools/list` returns the expected 38 registered tools before proceeding to `tools/call` scenarios.
6. Build the function dependency map before execution, then derive the test sequence priority from that dependency map rather than file-discovery order.
7. Perform end-to-end live integration testing in dependency order via async `tools/call` invocations.
8. Address any implementation, runner, data-contract, MCP transport, or scenario-ordering issues found during live execution.
9. Retest affected scenarios, then rerun the full dependency-ordered suite until all required calls pass with zero unexpected error responses.
10. Export the final per-function arguments and outputs into the project `docs/` directory as a dated results file.

## 6. Execution Order

```text
[initialize handshake] → items → requests → quotes → pricing → installments → files → segments → availability → cancellation → catalog
```

**Reason for ordering:** this project is an RFQ processor facade; item/provider validation must precede request creation, request/provider assignment must precede quote creation, quote pricing must precede installment validation, and cancellation/catalog readbacks are reference checks. Bundle scenarios are omitted (DDS dataset has 0 bundles). The MCP `initialize` handshake is implicit — `MCPHttpClient.__aenter__` calls `initialize()` automatically before any `tools/call`.

**Sequence construction rule:** the execution order must be rebuilt or revalidated before each certification run from the actual function dependencies in the runner and codebase. Static file order is not sufficient.

## 8. Failure and Resilience Scenarios

| Scenario | Injected fault | Expected behavior |
|---|---|---|
| missing gateway | stop gateway before live execution | `MCPHttpClient` connection fails; `_get_gateway_token` raises `ConnectionError`; script exits with FATAL message |
| invalid credentials | bad auth env values | `/auth/token` returns 401; token request fails; no tests execute |
| MCP daemon not loaded | `mcp_hospirfq_processor` not loaded into daemon engine | `tools/list` returns 0 tools or `tools/call` returns JSON-RPC error with method-not-found |
| PostgreSQL unreachable (when `DB_BACKEND=postgresql`) | unset `DATABASE_URL` or stop the local Postgres instance | gateway GraphQL calls return a clear persistence error; `tools/call` responses contain in-band error envelope; runner reports blocked; no partial certification |
| schema not at head (when applicable) | skip `alembic upgrade head` | migration readiness gate fails; testing blocked at dependency state `initialized` |
| KGE unreachable | stop `knowledge_graph_engine` or Neo4j | `tools/call inquire_catalog` returns error or empty payload; catalog inquiry fails with clear KGE error |
| stale seeded IDs | prepared DDS dataset IDs missing from the active backend | affected `tools/call` returns MCP content with in-band error envelope |
| MCP content parse failure | gateway returns non-JSON text in MCP content | `_parse_mcp_content` returns raw string; result tracking records it |
| SSE response instead of JSON | gateway returns `text/event-stream` | `MCPHttpClient._parse_sse_response` extracts JSON-RPC payload from SSE data lines |
| premature hold expiry | expire a fresh 15-minute hold | expected no-op envelope is recorded via `tools/call expire_availability_hold` |
| batch capacity exhausted | select a batch with `availabilityQty=0` (if any exist after prior holds) | availability check returns zero; hold acquire fails with clear capacity error |
| price tier segment mismatch | query price tiers for a segment UUID not in the prepared data | no tiers returned; pricing calculation uses default/base price |
| discount prompt scope mismatch | query discount prompts for an item UUID with no item-scoped prompts | empty result set; no error |
